# 正式學號登入長期過渡規劃

更新日期：2026-10-21（民國 115 學年度）

## 目的與現況

目標是由「班級＋座號＋原有密碼」逐年過渡到全校「正式學號＋原有密碼」，同時完整保留既有遊戲進度、成績、登入紀錄與活動足跡。

第一階段已建立：

- `students.school_student_id`：校方正式學號，僅作額外登入識別碼。
- `system_settings.student_number_login_enabled`：七年級雙重登入開關。
- `login_logs.login_method`：記錄 `class_seat`、`school_student_id` 或 `anonymous`。
- 前台七年級可在正式學號與班級座號之間選擇，兩者共用原有 `pin_code`。
- 後台可一鍵關閉正式學號入口，回復原有單軌制。

第一階段的執行與回復方式見 `docs/student-number-login-phase1.md`。

## 資料模型的不變原則

目前 `students.student_id` 通常由班級與兩位座號組成，並已被大量資料表當成遊戲帳號／進度關聯鍵。它不是未來要顯示給學生的正式學號。

永久規則如下：

```text
學生輸入正式學號＋原有密碼
  → 用 school_student_id 與 pin_code 找到既有 students 資料列
  → 取得該資料列原有 student_id
  → 所有遊戲繼續用原有 student_id 讀寫既有進度
```

禁止直接把正式學號覆寫到 `student_id`。若未來要全面改用 `students.id`（UUID）作關聯鍵，必須另立大型遷移專案，盤點並遷移所有引用表、RPC、Cookie、紀錄與遊戲狀態，不得混入一般升班作業。

## 預定過渡時程

### 115 學年度（2026 年 8 月起）

- 七年級：正式學號與班級座號雙重登入。
- 八、九年級：維持原有班級座號登入。
- 蒐集正式學號登入成功率、錯配、缺漏與回復紀錄。

### 116 學年度（2027 年 8 月起）

- 新七年級：匯入正式學號並開放學號登入。
- 原七年級升八年級：保留正式學號與既有內部遊戲帳號。
- 七、八年級：學號登入；是否暫留舊入口由驗收結果決定。
- 九年級：維持舊制，除非已取得並完成全體學號核對。

### 117 學年度（2028 年 8 月起）

- 七、八、九年級皆具備正式學號。
- 先進入全校雙重登入觀察期。
- 通過全面切換門檻後，改為「正式學號＋原有密碼」單軌制。
- 保留後台回復雙重制或原有制的緊急開關至少一學期。

若能提早取得八、九年級完整正式學號，可加速時程，但仍須逐班核對及通過相同驗收門檻。

## 下一版設定模型

目前布林值只能表示開或關。第二階段應升級成明確的登入政策，例如：

```text
student_login_mode:
  legacy_only       原有班級座號單軌制
  dual              正式學號與班級座號並存
  school_id_only    正式學號單軌制

student_number_login_grades:
  [7]
  [7, 8]
  [7, 8, 9]
```

後台需提供：

- 登入模式三選一。
- 開放正式學號登入年級的核取方塊。
- 各年級總人數、已有正式學號人數、缺漏人數及重複檢查結果。
- 切換到正式學號單軌制前的阻擋檢查。
- 一鍵回復上一個安全模式。
- 設定異動時間、操作者及前後值的稽核紀錄。

不得只靠前端隱藏控制安全模式；資料庫設定是權威來源，前端則必須在欄位缺失或讀取失敗時安全回到 `legacy_only`。

## 每學年升班與匯入流程

1. 備份 `students` 與所有進度關聯資料，記錄備份時間與筆數。
2. 先以預覽模式解析新名冊，不直接寫入。
3. 使用正式學號識別既有學生；班級、座號與姓名只作核對及更新資料。
4. 新增真正的新生；不得因升班而建立重複學生。
5. 列出缺學號、重複學號、姓名不一致、找不到既有學生及跨年級異常。
6. 人工處理所有異常後才正式寫入。
7. 抽查登入、進度、成績、足跡、特殊班級與教師查詢。
8. 先開放雙重登入，再依監測結果決定是否關閉舊入口。

匯入操作必須可重複執行且結果一致；網路中斷後重跑不得新增重複學生。正式名冊含個人資料，不得提交進 Git。

## 全面切換門檻

只有以下條件全部成立，才可啟用 `school_id_only`：

- 在校生正式學號覆蓋率為 100%。
- 正式學號唯一性檢查通過，沒有重複值。
- 學號、姓名、年級、班級及座號均已核對。
- 每一班至少完成抽樣登入，並確認兩種入口看到相同既有進度。
- 學生升班後進度、成績及活動足跡未中斷。
- 教師可依正式學號、姓名、原班與特殊班級查詢。
- 密碼重設流程可用，且仍使用原有密碼規則。
- 登入紀錄能辨識登入方式並支援班級篩選。
- 回復程序已在非正式環境演練成功。
- 已公告切換時間與舊入口停用方式。

若任何一項不成立，維持雙重登入，不得強制切換。

## 回復策略

回復優先順序：

1. `school_id_only` → `dual`：重新顯示班級座號入口。
2. `dual` → `legacy_only`：關閉正式學號入口，恢復原有畫面。

回復只改登入政策，不應：

- 刪除 `school_student_id`。
- 修改 `pin_code`。
- 覆寫 `student_id`。
- 搬移或刪除任何進度。
- 強制建立新學生帳號。

模式切換只影響之後的登入；已登入工作階段是否強制失效應另設明確選項，不應隱含在回復操作中。

## 後續 AI agent 的工作準則

接到「擴大學號登入」「升班」「全面學號制」或「回復舊制」要求時，AI agent 應先：

1. 讀取本文件與第一階段文件。
2. 檢查目前資料庫欄位、登入模式、開放年級及正式學號覆蓋率。
3. 盤點目標年級的缺漏與重複，不以猜測補學號。
4. 說明本次是程式部署、資料庫遷移、資料匯入或開關切換中的哪幾項。
5. 在修改前保留可回復路徑；在修改後驗證舊登入與新登入是否指向同一學生及同一進度。
6. 分別驗證新、舊兩個 GitHub 專案；不可假設兩者檔案樹完全相同。

任何無法確認的學生配對都應列入待處理清單，不可依姓名相似、排序或缺額直接寫入正式資料庫。
